Binutils编译错误

发表于2026-03-25|更新于2026-03-27|链接器/Binutils
|浏览量:

最近我在 Ubuntu 上编译 Binutils 2.42 时，gprofng 组件在链接阶段报错。最开始看上去只是一个普通的 undefined reference，但顺着错误一路排查下去，最后发现问题并不在最终链接命令本身，而在于一个中间生成文件异常，导致对应的目标文件成了“空壳对象文件”。
这篇文章记录一下这次排查的完整思路，也顺便总结一套处理类似链接错误的方法。

错误现象

从报错位置可以看出，这是一个典型的链接阶段错误：

  1. 出错程序是 /usr/bin/ld
  2. 未定义符号是 QL::Parser::*
  3. 调用位置在 DbeSession.cc 的 DbeSession::ql_parse() 函数中

其中最关键的是：

这说明：

  1. DbeSession.cc 中已经写了对 QL::Parser 的调用；
  2. 相关源码可以正常编译成 DbeSession.o；
  3. 但在最终链接生成 gprofng、gp-archive、gp-display-text 等可执行文件时，链接器找不到 QL::Parser 的实现。

换句话说，问题可以概括为：DbeSession.o 引用了 QL::Parser，但提供这些符号的目标文件没有正确提供实现。

排除过程

初步判断：这更像是项目内部对象缺失，而不是外部库问题

一开始面对 undefined reference，最自然的想法是：是不是少链接了某个库？
不过这次我没有优先怀疑 -lstdc++、-lfl、-ly 这类外部库，原因很简单：报错里的未定义符号并不是常见的 C 接口符号，比如 yyparse、yylex，而是一个明确的 C++ 类方法：

这更像是项目内部某个源码文件或自动生成文件没有正确参与构建，而不是单纯少传了一个系统库。进一步结合 gprofng 的代码结构，QL::Parser 这个名字很像是由 Bison 生成的 C++ parser 类。通常这类组件会有这样一条生成链：

而 Parser 类的实现，最合理的承载位置就是这个生成出来的 QLParser.tab.cc。
既然缺失的是 QL::Parser::*，而目录里正好有一个名为 QLParser.yy 的语法文件及其对应生成文件，那么 QL::Parser 的实现大概率就在 QLParser.tab.cc 里
于是我形成了第一个假设：QL::Parser 的实现应该来自 QLParser.tab.cc，而这个文件可能没有被正确生成，或者没有被正确使用。

首先排除工具版本问题：检查bison版本

既然怀疑问题和 Bison 生成链有关，第一步自然是先确认本机的 Bison 版本是否满足要求（上游确定bison版本应该大于3.0.4）：

检查生成文件：源码目录正常，构建目录异常

接下来需要检查 QLParser 相关文件在源码目录和构建目录中的状态。
我分别查看了 src 和 build 两边的文件：

这里立刻出现了一个很明显的异常：

  • 源码目录中的 QLParser.tab.cc 是一个正常大小的文件；
  • 构建目录中的同名文件 QLParser.tab.cc 却是 0 字节空文件。
  • 这说明构建目录中存在一个异常的中间文件。由于 out-of-tree build 往往会优先使用构建目录中的同名文件，因此一个损坏的 QLParser.tab.cc 很可能遮蔽掉源码目录中的正常文件，进而影响后续的编译结果。

到这里，问题已经缩小到很具体的范围：
| 构建目录中的 QLParser.tab.cc 异常，导致后续生成的 QLParser.tab.o 也可能有问题。

确认 Makefile 是否已经纳入该文件

为了避免误判，我又检查了 Makefile 中是否包含 QLParser 相关规则：

结果表明：

  1. QLParser.tab.cc 被列入构建体系；
  2. QLParser.tab.lo 也在对象列表中；
  3. BUILT_SOURCES 中明确包含 QLParser.tab.cc 和 QLParser.tab.hh。

这一步说明：
| 问题并不是“Makefile 根本没有构建它”，而是“它虽然被纳入了构建体系，但其生成或使用过程存在异常”。

继续往前推：问题到底出在最终链接，还是更早就埋下了？

为了进一步判断问题的位置，我查看了详细的链接日志，发现最终链接 gp-archive 时使用的是：

而报错来自：./.libs/libgprofng.a(DbeSession.o)

这说明：

  1. DbeSession.o 已经被正确打进了 libgprofng.a
  2. 最终链接命令也确实把 libgprofng.a 带进来了
  3. 因此，问题不太可能是“最终链接命令少链接了某个目标文件”

于是，真正该检查的就变成了：

  1. QLParser.tab.o 是否真的被打进了 libgprofng.a？
  2. QLParser.tab.o 本身是否真的包含 QL::Parser 的实现？

检查静态库内容：对象文件在库里，但实现并不在对象里：

输出是：QLParser.tab.o
这说明它确实已经被归档进 libgprofng.a。
接着再检查这个对象文件本身是否真的包含 QL::Parser 相关符号：

结果是：没有任何输出。这一步是整个排查过程中最关键的一步。
它说明：

  1. QLParser.tab.o 虽然存在；
  2. 也确实被打进了静态库；
  3. 但它并没有真正提供 QL::Parser::Parser、QL::Parser::parse()、析构函数等实现符号。

也就是说，问题并不是“目标文件没参与链接”，而是：
| QLParser.tab.o 自身就是一个错误的、没有有效实现的空壳对象文件。

最终定位：中间生成文件异常，导致目标文件失效

把前面的信息串起来，问题链条就很清晰了：

  1. DbeSession.o 依赖 QL::Parser::*；
  2. QL::Parser 的实现理论上应来自 QLParser.tab.cc；
  3. 构建目录中的 QLParser.tab.cc 异常地变成了 0 字节空文件；
  4. 编译系统优先使用了构建目录中的这个异常文件；
  5. 最终生成出的 QLParser.tab.o 没有任何 QL::Parser 实现；
  6. 虽然该对象文件被打进了 libgprofng.a，但其中并没有真正可用的符号；
  7. 因而在最终链接阶段触发了 undefined reference。

因此，最终可以把问题归纳为：
| 这不是一个普通的“少链接某个库”的问题，而是 gprofng 中 QLParser 相关中间生成文件异常，导致生成出来的目标文件不包含预期实现，最终在链接阶段暴露为 QL::Parser 未定义引用错误。

修改思路

既然已经确定源码目录中的 QLParser.tab.cc/.hh 是正常的，而构建目录中的对应文件是异常的，那么一种直接的验证和临时修复手段就是：

  1. 删除构建目录中的异常文件；
  2. 将源码目录中的正常 QLParser.tab.cc/.hh 复制到构建目录；
  3. 再重新编译相关目标。

这种方法的目的主要是验证判断是否正确。
不过更稳妥的方式仍然是：

  1. 清理整个构建目录；
  2. 重新执行 configure；
  3. 从头重新构建。

这样可以避免旧的中间文件、依赖文件或时间戳状态继续污染后续构建。

经验

这次问题其实很有代表性。以后再遇到类似的 undefined reference，最重要的是：==是谁在引用这个符号？这个符号本来应该由谁定义？==。前者告诉你报错从哪里暴露出来，后者才告诉你问题真正可能出在哪里。
也就是找到：

  • 它应该在哪个 .cc / .c 文件里实现
  • 或者应该在哪个生成文件里实现
  • 或者应该在哪个 .o / .a / .so 里提供

我觉得可以按下面这个顺序排查：

  1. 先区分是编译错误还是链接错误：如果报错来自 ld，通常就是链接阶段。
  2. 判断未定义符号属于外部库还是项目内部对象：如果是项目内部类、函数、命名空间符号，优先怀疑对象文件或自动生成文件。
  3. 找出该符号理论上应该由谁提供：先明确：这个符号本该来自哪个 .cc、.c、.o、.a。
  4. 检查相关生成文件是否正常
    包括：
    文件是否存在
    文件大小是否异常
    是否被错误覆盖
    是否在 build 目录和 source 目录之间不一致
  5. 检查目标文件中是否真的包含该符号
    这一步非常关键：nm -C xxx.o | grep SymbolName
  6. 检查目标文件是否真的进入静态库或最终链接
    ar t libxxx.a

在这类问题里，nm -C 和 ar t 基本可以说是最有效的两把刀。
